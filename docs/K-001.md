# K-001: counter implementation and test plan

**PLANNED — approval required before implementation.** No source or native validation is delivered by this plan.

## Scope and sequence

1. Obtain operator evidence for native Fedora confinement covering inside writes, parent/sibling read/write denial, symlink escape, protected paths, temporary roots, network policy and available integrations. The existing checklist says NOT VERIFIED; do not infer verification from session permissions. Reconcile its historical network/publication policy with the current explicit authorization without changing external configuration.
2. Inventory the actual Fedora Rust, C++ compiler, Qt 6, QML tools, Kirigami and CXX-Qt compatibility. Select pinned/reproducible versions, crate/module identifiers and proposed licence only after reviewing upstream support and dependency licences. Do not install packages or fetch dependencies from sandbox commands without separately authorized operator provisioning.
3. Create the smallest Cargo-first library experiment: one Rust counter state, an observable integer and one increment action, a label and a native button. Define initial value, integer bound behavior and notification semantics before coding. Keep state changes on the appropriate Qt thread; avoid unnecessary asynchronous or abstraction layers.
4. Expose Rust reuse and a narrow CXX-Qt QObject bridge. Use supported Qt/Kirigami controls and semantic theme colors, spacing and typography. Define whether the component receives caller-owned state or creates its own state; document ownership and lifetime. Avoid a global singleton requirement.
5. Establish real QML deployment: generated registration/plugin metadata, module files, runtime libraries and installation/import path. Test from an unrelated working directory with the source tree unavailable to imports. If Cargo cannot reasonably produce an independently installable module, record concrete failure evidence before proposing minimal CMake support.
6. Add separately rooted downstream Rust and QML consumers in `smoke/`, with manifests/imports that use only the intended public surface. Validate staged installation or a packaged Rust artifact, not private module paths or a workspace-only dependency illusion. Keep outputs under ignored `.work/` or `target/`; retain source fixtures and reproducible commands.
7. Record exact dependency versions, commands, outcomes, runtime environment, limitations and manual operator evidence. Update requirements and developer instructions only with observed working procedures.

## Acceptance tests

| Test | Required evidence |
| --- | --- |
| State | Defined initial value, repeated increments and explicit bound behavior; no panic or wraparound surprise |
| Binding | Label changes after every effective action; notification count and multiple component instances behave as specified |
| Rust consumer | Clean external consumer builds and runs using the documented public API and artifact |
| QML consumer | Independent engine imports installed module and operates counter without private source imports or demo bootstrap |
| Cargo-first build | Reproducible clean build with reviewed/provisioned dependencies; record any packaging failure motivating CMake |
| Keyboard | Tab/Shift+Tab focus traversal, visible focus and Space/Enter activation follow supported control semantics; no mouse required |
| Accessibility | Inspect names/roles/value, screen-reader announcement and focus order; record tool/version and manual result |
| Native KDE | Observe light/dark, configured fonts, scaling and control states on Fedora KDE; document whether settings require restart |
| Isolation | Independent instances do not share state unexpectedly; teardown produces no relevant QML/runtime errors |
| Documentation | A downstream developer can repeat both consumers from recorded commands and requirements |

Automate state, bridge and QML interaction checks where practical; record manual native and accessibility checks separately. Missing evidence is UNVERIFIED, not a pass. K-001 is accepted only after both downstream proofs and the native keyboard/accessibility checks pass or an explicit scope change is approved.

## Later calculator compatibility

Reserve no speculative common framework. After K-001, use a calculator example to compare consumer workflows across independent KDE, GNOME and Unified libraries: create a view, bind display state, connect actions and run. Each example owns its math/state and covers digits, decimal, +, -, *, /, equals, clear, malformed input and division by zero. Agree shared behavior cases through documentation and tests, not a fourth shared repository. Toolkit-specific setup is allowed; near-parity concerns high-level usage. Unified integration and any frontend replacement require separate lifecycle/state proofs and do not imply instant GTK/Qt swapping.
